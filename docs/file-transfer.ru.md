# Отправка файлов

Файл размером до 32 ГиБ (по умолчанию) идёт от одного контакта к другому напрямую, от пира к пиру:
прямо по QUIC, если они могут соединиться, или через цепочку релея, если не могут. Никто другой,
включая релей, не может его прочитать или изменить. Код находится в `echofog-core-oss/internal/services/filexfer`.

## Что получатель узнаёт сначала

Отправитель один раз читает файл и строит над его кусками по 64 КиБ дерево Меркла на SHA-256
(дерево из RFC 6962: листья — `SHA-256(0x00 ‖ кусок)`, внутренние узлы —
`SHA-256(0x01 ‖ левый ‖ правый)`; корень называет содержимое, как корень кусков в BitTorrent v2).
Затем он отправляет обычное сообщение в чат, зашифрованное сквозным шифрованием, как любое
сообщение, в котором есть:

- имя, размер и MIME-тип файла,
- корень дерева Меркла,
- ID передачи и свежий случайный 32-байтный ключ,
- для картинки JPEG, PNG или GIF — миниатюра (JPEG не больше 192 px по длинной стороне и 6 КБ),
  чтобы чат показал картинку ещё до того, как файл скачан.

Отправитель не отдаёт файл больше своего лимита (по умолчанию 32 ГиБ: пока он раздаёт файл, его
дерево лежит в памяти, при таком размере это 32 МиБ). Пока получатель не примет файл, ничего не
передаётся. Сначала получатель сверяет размер с тем же лимитом и со свободным местом на диске.

## Как идут байты

Получатель сам запрашивает данные. Он просит недостающие куски кадрами *want*; отправитель отвечает
на каждый кадром *chunk*, в котором лежит кусок и его путь проверки (соседние хеши до корня, по 32
байта на уровень дерева). Получатель проверяет каждый кусок по корню сразу, как тот пришёл, как в
проверяемой потоковой передаче Bao/iroh. Поэтому кусок, не принадлежащий файлу, никогда не
записывается, и список кусков заранее не нужен.

Каждый кадр запечатан XChaCha20-Poly1305. Для двух направлений используются разные ключи,
выведенные из ключа предложения, а заголовок кадра (тип, ID передачи) аутентифицирован. Поэтому
релей не может ни прочитать, ни изменить, ни подсунуть, ни отразить кадры обратно. Кадр, который не
открывается, отбрасывается.

Управление потоком устроено как в TCP: получатель держит окно кусков «в пути», увеличивает его,
пока куски возвращаются быстро, уменьшает вдвое при потере и запрашивает заново то, что не пришло
вовремя. Отправитель шлёт несколько кадров сразу и подстраивает их число под скорость отправки.

## Перерывы

- **Обрыв связи.** Передача, которая какое-то время ничего не получает, показывает *Ждём, когда
  собеседник снова будет в сети…*, пытается переподключиться (DHT, пробивка NAT, релей) и сама
  продолжается, когда пир снова доступен. Сама по себе она никогда не сдаётся.
- **Перезапуск приложения.** Получатель пишет куски в `<имя>.<id8>.part` (`<id8>` — первые 8
  символов ID передачи) и отмечает, какие у него есть, только после того как они сброшены на диск.
  После перезапуска он продолжает с того же места.
  Отправитель снова раздаёт файл, проверив, что у файла по-прежнему тот же корень, что был
  предложен.
- **Повреждение.** Когда файл получен целиком, он хешируется ещё раз. Если хеш не совпадает
  (частичный файл изменили, пока приложение было закрыто), файл скачивается заново.
- **Отмена / отказ.** Любая сторона может остановить передачу; частичный файл удаляется, а другой
  стороне об этом сообщается.

## В группе

Файл, отправленный в группу, уходит одним групповым сообщением (зашифрованным сквозным шифрованием
для каждого участника, как любое групповое сообщение) с одним ID передачи и одним ключом для всех.
Каждый участник, принявший файл, скачивает его у отправителя своей передачей, со своим окном и
прогрессом. Отправитель раздаёт всем из одного открытого файла, каждому из своей очереди, и считает,
у кого файл есть целиком (на его карточке это видно как «скачали 2 из 4»). После этого предложение
остаётся открытым для тех, кто примет позже, пока отправитель не перестанет раздавать — об этом
узнают все участники.

Поскольку ключ есть у каждого участника, участник называет себя (свой peer ID) внутри каждого
запечатанного кадра, который шлёт отправителю, чтобы тот знал, кому отвечать. Отправитель отвечает
только участникам: тем, кому файл был предложен, или тем, кого группа сейчас считает участниками
(кто вступил позже). Релей по-прежнему ничего не узнаёт: имя лежит внутри запечатанного тела.
Участник может выдать себя за другого участника, но это лишь заставит отправителя прислать тому
куски, которые тот не просил; ничего сверх того, что он и так мог скачать, он не получит. В истории,
которую получает новичок, файловое сообщение передаётся только как имя, без предложения.

## На диске получателя

Файлы сохраняются в `Downloads/EchoFog` (или в `storage.download_dir`). Имя, которое дал
отправитель, сводится к простому имени файла: без папок, без `..`, без символов и имён устройств,
которые запрещает Windows, без невидимых знаков направления текста; существующий файл никогда не
перезаписывается (`имя (1).ext`). В Windows полученный файл помечается как скачанный из интернета
(Mark of the Web), поэтому система предупредит перед запуском программы из него, а приложение
спросит перед открытием файла, который запустил бы код.
