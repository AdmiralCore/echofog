# Нода протокола v2 на VPS

Это полный путь от чистого сервера до работающей ноды EchoFog v2: ретранслятора, почтового ящика и
DHT-сервера, при желании — с выходом. Все пути, имена переменных и порты сверены с файлами ветки
`v2`: `deploy/v2/.env.example`, `deploy/v2/docker-compose.yml`, `deploy/v2/entrypoint.sh`,
`deploy/v2/Dockerfile` и `deploy/v2/install.sh`. Все адреса — заглушки из документационных
диапазонов: `203.0.113.10` означает публичный адрес сервера.

Руководство для протокола v1 — [deploy-vps.ru.md](deploy-vps.ru.md).

> **Статус.** Протокол v2 — это линия 0.3.0, и она ещё экспериментальная: независимого аудита
> безопасности сторонней организацией не было. Не держите в кошельке ноды больше TON, чем готовы
> потерять.

## 1. Что получится и что нужно

Нода берёт на себя те роли, которые ей заданы: передаёт звонки и сообщения между людьми, которые не
могут соединиться напрямую, хранит сообщения для тех, кто офлайн, и держит часть DHT — общей
адресной книги сети. Роли перечисляются в `ECHOFOG_ROLES`; сколько трафика стоит каждая, написано в
[«Запуск ноды»](run-a-node.ru.md).

Контейнер работает от непривилегированного пользователя, с файловой системой только для чтения, без
Linux-привилегий и без возможности их получить. Операторский API остаётся на loopback внутри
контейнера, обращаться к нему нужно через `docker compose exec`; наружу не публикуется ни
операторский, ни отладочный порт. Профиль (identity, `server.json`, токен оператора) лежит в томе
`echofog-v2-data` по пути `/data`.

Без обложки у ноды **нет публичной карточки**: она обслуживает только тех, у кого уже есть её ссылка,
по noise3. В этом режиме нода слушает только UDP, поэтому проверка TCP на порту 443 получает отказ,
даже когда нода исправна. Для публичной карточки нужны и домен, указывающий на сервер, и папка с
собственным сайтом оператора.

Что нужно от сервера:

- Ubuntu 22.04 и новее или Debian 12 и новее, доступ root.
- Публичный IPv4- или IPv6-адрес, до которого интернет дотягивается на опубликованных портах. В
  некоторых облаках у машины на интерфейсе приватный адрес, а публичный стоит перед ней через NAT:
  это работает, если провайдер пробрасывает порты.
- Порт 443, доступный по **TCP и UDP**. Compose-файл ограничивает контейнер 1 ГБ памяти и 512
  процессами, поэтому столько свободной памяти нужно планировать.
- Свободное место для Docker и образа. Точной цифры здесь нет: образ меняется с каждой сборкой,
  поэтому перед началом посмотрите `df -h /`. Данные самой ноды небольшие, а журналы контейнера
  compose-файл ограничивает 100 МБ (пять файлов по 20 МБ).

## 2. Подготовка чистого сервера

Команды ниже рассчитаны на root-оболочку (`sudo -i`); при работе от обычного пользователя добавьте
`sudo`. Начните с системных пакетов:

```sh
apt update && apt -y upgrade
apt -y install ca-certificates curl
```

Проверьте часы. Пир отклоняет рукопожатие, если часы расходятся больше чем на десять минут, а
сертификат обложки сверяется с системным временем:

```sh
timedatectl status        # "System clock synchronized: yes"
```

Если синхронизации нет, поставьте и включите службу времени:

```sh
apt -y install systemd-timesyncd && timedatectl set-ntp true
```

Проверьте диск:

```sh
df -h /
```

## 3. Установка git и Docker

Нода запускается из git-клона и из опубликованного образа, поэтому нужно и то и другое. Docker
ставится из собственного репозитория Docker: он приносит плагин `compose`, а в пакетах дистрибутива
его может не быть. Команды работают и на Ubuntu, и на Debian: `ID` в `/etc/os-release` равен `ubuntu`
или `debian`, что совпадает с путями репозитория.

```sh
apt -y install git
install -m 0755 -d /etc/apt/keyrings
. /etc/os-release
curl -fsSL "https://download.docker.com/linux/${ID}/gpg" -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/${ID} ${VERSION_CODENAME} stable" \
  > /etc/apt/sources.list.d/docker.list
apt update
apt -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Проверьте, что демон и плагин compose работают:

```sh
docker version
docker compose version
docker run --rm hello-world
```

`hello-world` печатает приветствие и удаляется. Если он не запустился, сначала почините Docker:
дальше ничего работать не будет.

Альтернатива — удобный скрипт Docker с `https://get.docker.com`. Он ставит последнюю версию без
закрепления и без собственного подписанного apt-источника, поэтому перед запуском его стоит прочитать.

Инструкции в этом руководстве рассчитаны на root-оболочку. При работе от обычного пользователя
добавляйте `sudo` либо включите пользователя в группу `docker` и войдите заново:

```sh
usermod -aG docker youruser
```

Членство в группе `docker` на этом хосте равносильно root: оно позволяет запустить контейнер, который
смонтирует любой путь хоста. На общей машине это стоит учитывать.

## 4. Клон ветки `v2`

В репозитории лежат оба продукта и оба протокола. Нода v2 — в ветке `v2`; `main` и `dev` по-прежнему
собирают ноду v1 (`echofog-node run`). Клонируйте только нужную ветку:

```sh
git clone --branch v2 --single-branch https://github.com/AdmiralCore/echofog.git
cd echofog/echofog-core-oss
```

Убедитесь, что ветка та:

```sh
git branch --show-current     # v2
git log -1 --oneline
```

Образ контейнера собирает workflow `node-image` из этой ветки и публикует как
`ghcr.io/admiralcore/echofog-node`. Тег `v2-dev` следует за каждым пушем в `v2`; теги `latest` и `dev`
— это нода v1, здесь они не используются. У каждой сборки есть ещё `sha-<коммит>`: его закрепляют,
когда обновлять ноду хотят только вручную.

## 5. Настройка `deploy/v2/.env`

```sh
cp deploy/v2/.env.example deploy/v2/.env
```

Выберите команду Compose для своего варианта; дальше в руководстве она обозначается `$DC`. Без
обложки это базовый файл, с обложкой добавляется override-файл, описанный ниже:

```sh
# без обложки
DC="docker compose -f deploy/v2/docker-compose.yml --env-file deploy/v2/.env"
# или с обложкой и смонтированным сайтом
DC="docker compose -f deploy/v2/docker-compose.yml -f deploy/v2/docker-compose.site.yml --env-file deploy/v2/.env"
```

Отредактируйте `deploy/v2/.env`. Значения, которые важны:

| Переменная | Что указать |
|---|---|
| `ECHOFOG_IMAGE` | `ghcr.io/admiralcore/echofog-node:v2-dev` или `...:sha-<коммит>`, чтобы закрепить сборку. |
| `ECHOFOG_ADVERTISE_ADDR` | **Обязательна при первом запуске.** Публичный IPv4- или IPv6-адрес сервера как IP-литерал. Имя отклоняется, контейнер завершается с ошибкой. |
| `ECHOFOG_PORT` | `443`. С обложкой здесь слушает reality2-quic по UDP и reality2-tcp по TCP; без обложки здесь слушает noise3 по UDP. |
| `ECHOFOG_NOISE_PORT` | `444`. Куда переезжает noise3, когда обложка занимает `ECHOFOG_PORT`. |
| `ECHOFOG_ROLES` | `relay,mailbox,dht-server`. Роли перечисляются через запятую; пустое значение выключает все роли. |
| `ECHOFOG_INVITES` | `true` открывает ещё один UDP-слушатель для ссылок-приглашений. Без обложки он занимает `ECHOFOG_PORT+1` (444), с обложкой — `ECHOFOG_NOISE_PORT+1` (445). |
| `ECHOFOG_COVER` | `node.example.org:443`. Имя должно разрешаться в `ECHOFOG_ADVERTISE_ADDR`. |
| `ECHOFOG_SITE_DIR` | `/srv/site`: папка с собственным сайтом оператора. Нужна вместе с `ECHOFOG_COVER`; обложку без неё контейнер отклоняет. |
| `ECHOFOG_COVER_CERT` | Пусто означает ACME. Иначе — путь к PEM-файлу с цепочкой сертификата домена и его ключом внутри контейнера. |
| `ECHOFOG_ACME_ACCEPT_TOS` | `true` фиксирует согласие с условиями центра сертификации. `false` отказывается от ACME и требует сертификат. |
| `ECHOFOG_ACME_EMAIL` | Необязательный контакт для ACME. |
| `ECHOFOG_ACME_CHALLENGE` | Пусто означает `tls-alpn-01`, для него нужен TCP 443. `http-01` требует ещё и TCP 80. Центр сертификации проверяет `tls-alpn-01` на порту 443 домена, поэтому обложке на другом порту нужен `http-01` или сертификат. |
| `ECHOFOG_DATA_DIR` | Оставьте `/data`. Профиль живёт в томе, смонтированном сюда. |

**Роль выхода.** `exit` в `ECHOFOG_ROLES` отдаёт соединение этого сервера другим: их трафик выходит в
интернет с этого IP-адреса, и правовая ответственность за него лежит на операторе. Включайте её
только на сервере и в стране, где это разрешено, и сначала прочитайте условия хостера. Подробнее:
[«Запуск ноды»](run-a-node.ru.md#про-выходной-узел).

**Роли, обложка и приглашения применяются один раз, при создании профиля.** Дальше нода читает
`/data/server.json`, и правка `.env` на них уже не влияет (тег образа и опубликованные порты
по-прежнему берутся из `.env`). Задайте эти значения до первого запуска. Чтобы изменить их позже,
остановите контейнер и отредактируйте `server.json` (в нём есть комментарии) во временном контейнере с
тем же томом:

```sh
$DC stop node
docker run --rm -it -v v2_echofog-v2-data:/data alpine sh -c \
  'vi /data/server.json && chown 1000:1000 /data/server.json && chmod 600 /data/server.json'
$DC start node
```

Имя тома подставьте то, которое показывает `docker volume ls`. Не создавайте новый профиль только
ради смены роли: если профиль в папке уже есть, `init` завершается ошибкой «already holds a server
profile» и ничего не заменяет. Identity теряется только на пустом томе, то есть после `$DC down -v`
(раздел 10).

Чтобы добавить приглашения в уже существующий профиль, в `server.json` нужен ключ:

```json
"invite_listen": { "suite": "noise3", "bind": "0.0.0.0:445", "advertise": "203.0.113.10" }
```

Затем опубликуйте тот же порт в override-файле (см. ниже).

### Обложка и Docker

`deploy/v2/docker-compose.yml` монтирует только том данных, поэтому папка хоста внутри контейнера не
видна. Ноде нужен `ECHOFOG_SITE_DIR` как путь внутри контейнера, и эту папку нужно смонтировать.
Добавьте override-файл:

```yaml
# deploy/v2/docker-compose.site.yml
services:
  node:
    volumes:
      - echofog-v2-data:/data
      - /srv/echofog-site:/srv/site:ro
    ports:
      - "445:445/udp"   # только с ECHOFOG_INVITES=true и обложкой
```

Оба монтирования указаны намеренно: контейнеру нужны и том профиля, и сайт. Сайт монтируется только
для чтения, так что файловая система контейнера остаётся read-only. Положите сайт в
`/srv/echofog-site` на хосте и сделайте его доступным на чтение всем: пользователь контейнера должен
его читать, а публичный сайт не является секретом. Затем задайте `ECHOFOG_SITE_DIR=/srv/site`. Если
используется собственный сертификат, смонтируйте его так же и укажите `ECHOFOG_COVER_CERT` на путь
внутри контейнера.

Отдельно про порт приглашений: базовый compose-файл публикует только `ECHOFOG_PORT` (TCP и UDP) и
`ECHOFOG_NOISE_PORT` (UDP), поэтому с обложкой и приглашениями слушатель на 445 недоступен, пока его
не опубликует override. Без обложки приглашения используют 444, а этот порт базовый файл уже
публикует.

## 6. Файрвол и панель провайдера

Сначала разрешите SSH, иначе можно закрыть себе доступ. Проверьте, какой порт SSH использует
провайдер, прежде чем выполнять эти команды.

```sh
apt -y install ufw
ufw allow 22/tcp
ufw allow 443/tcp
ufw allow 443/udp
ufw allow 444/udp
ufw allow 445/udp     # только с приглашениями и обложкой
ufw enable
ufw status
```

Если сервер в облаке, те же порты нужно открыть в его собственном файрволе или security group;
одного `ufw` недостаточно. UDP важен не меньше TCP: основной путь — QUIC поверх UDP, и нода с
закрытым UDP выглядит живой, но пиров не получает. Закрытый UDP-порт нельзя проверить простым
подключением: ответа не будет в обоих случаях.

## 7. Запуск ноды

`$DC` — это сокращение, выбранное в разделе 5. Посмотрите, что собирается сделать Compose, затем
скачайте образ и запустите:

```sh
$DC config
$DC pull
$DC up -d
```

`config` печатает итоговую конфигурацию, включая окружение из `.env`: перед первым запуском проверьте
образ и опубликованные порты, а вывод не публикуйте в открытых обсуждениях. Образ публикуется для
`linux/amd64` и `linux/arm64`; на другой архитектуре соберите его из
`echofog-core-oss` командой `docker build -f deploy/v2/Dockerfile -t echofog-node:v2-local .` и
задайте `ECHOFOG_IMAGE=echofog-node:v2-local`.

При первом запуске entrypoint создаёт профиль в томе и затем запускает ноду. Следите за ней:

```sh
$DC ps
$DC logs -f --tail=100 node
```

`ps` показывает контейнер и его здоровье. В образе есть healthcheck: он раз в 30 секунд запускает
`echofog-node v2 status --data /data`, с 40-секундным стартовым периодом и тремя повторами. `healthy`
означает, что нода работает и её операторский API отвечает на loopback; `unhealthy` — что процесс
идёт, но API не отвечает; `starting` нормально в первые секунды. Причину цикла перезапусков видно в
`logs`; чаще всего это пустой или неверный `ECHOFOG_ADVERTISE_ADDR`.

Если `pull` отказывает с ошибкой доступа или «denied», пакету может требоваться авторизованный
запрос. Создайте personal access token GitHub с областью `read:packages` и войдите: команда спросит
токен, поэтому он не попадёт в историю оболочки:

```sh
docker login ghcr.io -u <github-user>
```

Не кладите токен в `.env`, скрипт или репозиторий. Ошибка «manifest unknown» означает, что тега нет:
проверьте `deploy/v2/.env` и теги образа.

## 8. Первый запуск: фраза восстановления, статус, приглашения, карточка

Фраза восстановления записывается один раз в файл в томе и никогда — в журнал контейнера.
Скопируйте её в надёжное место и удалите файл:

```sh
$DC exec node cat /data/recovery-phrase.txt
$DC exec node rm /data/recovery-phrase.txt
```

Фраза восстанавливает identity ноды и её кошелёк. Тот, у кого она есть, управляет нодой; храните её
вне сервера.

Посмотрите на ноду:

```sh
$DC exec node echofog-node v2 status --data /data --plain
$DC exec node echofog-node v2 doctor --data /data
```

`status` показывает роли, носители, сессии, трафик, обложку и сертификат, а при наличии публичной
карточки — публичную ссылку. `--plain` убирает цвет, чтобы вывод оставался читаемым в журнале.
`doctor` проверяет конфигурацию, права на файлы, порты, часы, свободное место, обложку (домен, папку
сайта и то, что сайт свой) и её сертификат; наружу он ничего не отправляет, пока не добавлен `--dns`.
Когда нода запущена, он сообщает, что порты заняты нодой, а не пытается занять их сам.

Приглашениям нужен `ECHOFOG_INVITES=true` **при первом запуске**; с умолчанием `false` нода отвечает,
что приглашения не настроены. Создайте приглашение со сроком доступа:

```sh
$DC exec node echofog-node v2 invite create --data /data --access 30d
$DC exec node echofog-node v2 invite list --data /data
```

`invite create` печатает ссылку; `--access 30d` — сколько человек может пользоваться нодой,
`--link 7d` ограничил бы срок самой ссылки, а `--max-entries` — число людей по ней. Передавайте
ссылку по каналу, которому доверяете.

**Публичная карточка.** С обложкой `status` печатает публичную ссылку (и подходящую строку для списка
узлов), когда карточка выпущена. Для этого DNS домена должен указывать на `ECHOFOG_ADVERTISE_ADDR`, в
папке сайта должно быть содержимое, а сертификат — выпущен. Без обложки публичной карточки нет по
замыслу: нода работает только для своих по noise3.

Экран установщика рисует QR-код для ссылки, когда подписанный релиз сделает его доступным (раздел 12).
В пути через Docker команды для QR нет: возьмите ссылку из `status` или `invite create` и закодируйте
её любым офлайновым генератором QR.

Проверьте, что порт открыт снаружи, с другой машины:

```sh
nc -vz 203.0.113.10 443
```

Если `nc` нет, поставьте там `netcat-openbsd`. Так проверяется только TCP. Для UDP честная проверка —
подключившийся пир: `status` показывает сессии, а `doctor` сообщает о доступности с точки зрения самой
ноды. Если никто не подключается, причина в файрволе, панели провайдера или неверном
`ECHOFOG_ADVERTISE_ADDR`.

## 9. Обновление

```sh
git pull --ff-only
$DC pull
$DC up -d
```

`git pull` обновляет compose-файл, пример конфигурации и это руководство; `pull` скачивает образ, на
который указывает тег; `up -d` пересоздаёт контейнер, если что-то изменилось. Профиль остаётся в томе,
поэтому identity, конфигурация и кошелёк сохраняются.

Чтобы закрепить сборку, задайте образ по тегу коммита, например
`ECHOFOG_IMAGE=ghcr.io/admiralcore/echofog-node:sha-1234567`, и выполните `$DC pull && $DC up -d`.
Тогда обновление — это осознанная правка этой строки. Для отката верните предыдущий тег `sha-` и
выполните те же две команды: данные в томе не затрагиваются. Если `git pull` изменил
`docker-compose.yml` или entrypoint, прочитайте diff до запуска нового образа.

Перед сменой версии, в которой есть сомнения, сделайте копию тома. Имя тома показывает
`docker volume ls` (Compose добавляет к нему имя проекта, по умолчанию `v2_echofog-v2-data`); команда
ниже выкладывает профиль в текущую папку, используя `tar` из образа `alpine`:

```sh
docker run --rm -v v2_echofog-v2-data:/data -v "$PWD":/backup alpine tar czf /backup/echofog-data.tar.gz -C /data .
```

## 10. Удаление ноды

```sh
$DC down
```

Команда удаляет контейнер и сеть. Профиль остаётся в томе. Чтобы удалить и данные:

```sh
$DC down -v
```

**Это удаляет identity и кошелёк.** Без фразы восстановления ноду не восстановить, а TON на её
кошельке станет недоступен. Делайте так, только если это действительно нужно. Затем удалите клон:

```sh
cd ../.. && rm -rf echofog
```

## 11. Если что-то не работает

| Симптом | Причина | Что делать |
|---|---|---|
| `up` падает с «address already in use» | TCP- или UDP-порт 443 держит другой процесс: веб-сервер, прокси, старая нода | `ss -lntup \| grep ':443'`, остановите другой процесс или задайте другой `ECHOFOG_PORT` и откройте его в файрволе |
| Контейнер перезапускается по кругу, в журнале `ECHOFOG_ADVERTISE_ADDR is required` | Переменная пуста | Укажите публичный IP-литерал в `.env` и выполните `$DC up -d` |
| В журнале `must be an IPv4 or IPv6 literal, not a name` | В `ECHOFOG_ADVERTISE_ADDR` попало доменное имя | Укажите адрес; домен — это `ECHOFOG_COVER` |
| В журнале `ECHOFOG_SITE_DIR is required with ECHOFOG_COVER` | Обложка без папки сайта | Задайте `ECHOFOG_SITE_DIR` и смонтируйте папку (раздел 5) либо очистите `ECHOFOG_COVER` |
| `pull` получает отказ | Реестр требует авторизованного запроса или тег неверен | `docker login ghcr.io` с токеном `read:packages` либо проверьте тег |
| Публичной карточки нет, хотя обложка задана | DNS не указывает на сервер, папка сайта пуста или чужая, заказ ACME не удался | `$DC exec node echofog-node v2 doctor --data /data --dns`, откройте TCP 443 (и 80 для `http-01`), проверьте, что в сайте есть `index.html` |
| Публичной карточки нет, обложки нет | Так и задумано | Добавьте домен и папку сайта либо оставьте ноду для своих |
| Пиры не подключаются, `status` показывает ноль сессий | UDP 443 закрыт в `ufw` или в панели провайдера, либо `ECHOFOG_ADVERTISE_ADDR` не тот адрес, который видит интернет | Откройте 443/udp в обоих местах; сверьте адрес с консолью провайдера |
| Приглашения отклоняются | `ECHOFOG_INVITES` был `false` при первом запуске | Отредактируйте `server.json` и добавьте слушатель приглашений (раздел 5) либо на ещё не используемой ноде начните с пустого тома; затем опубликуйте порт |
| Предупреждения о часах в `status` или `doctor` | Время не синхронизировано | `timedatectl set-ntp true` |
| `doctor` сообщает, что мало места | Образы Docker, журналы или данные самого хоста | `docker system prune`, проверьте `df -h /`; размер журналов ограничен compose-файлом |
| `exec` сообщает, что нода не запущена | Контейнер остановлен или в профиле нет `operator.addr` | `$DC ps`, `$DC logs --tail=100 node` |
| `cat`, `exec` или запись в `/data` отвечают `Permission denied`, либо `doctor` пишет, что файл или каталог доступен посторонним | Файлы тома принадлежат другому uid (их правили с хоста под root) или у них выставлены биты group/other, а узел работает как `1000:1000` (`user:` в compose-файле) и entrypoint ставит `umask 077` | `$DC stop node`, затем во временном контейнере `chown -R 1000:1000 /data`, `chmod 700` на каталог и `600` на его файлы (раздел 5), `$DC start node`. `server.json` правьте только так, потом выполните `$DC exec node echofog-node v2 doctor --data /data` |
| Здоровье `unhealthy` | Процесс идёт, но операторский API не отвечает | Прочитайте журнал; API записывает `operator.addr` в `/data` при старте |

## 12. Установка без Docker

Для сервера без Docker есть нативный путь: `deploy/v2/install.sh` проверяет подписанный релиз и
затем запускает `echofog-node v2 setup`, который создаёт системного пользователя `echofog`, папку
данных `/var/lib/echofog` (права 0700) и unit systemd и включает службу. Файрвол он сам не меняет:
печатает команды и выполняет их только с `--open-ports`.

**Сейчас этот путь непригоден, и руководство не делает вид, что это не так.** `install.sh` в
репозитории — шаблон: блок ключей релиза в нём `PLACEHOLDER`, поэтому скрипт останавливается, ничего
не проверив. В open-source сборке `echofog-node` ключей релиза тоже нет, поэтому `v2 setup`
завершается с «this build has no release keys». Оба станут рабочими, когда появится подписанный
релиз с блоком ключей; корень доверия, правило `min_version` и смена ключей описаны в
[«Доверие к релизам»](release-trust.ru.md).

Когда подписанный релиз появится, рабочий порядок будет таким:

```sh
curl --proto '=https' --tlsv1.2 -fsSL -o install.sh https://example.org/install.sh
sha256sum install.sh               # сверьте значение с сайтом и README
sh install.sh --fingerprint        # тот же SHA-256 целого файла, затем отпечаток блока ключей
ECHOFOG_RELEASE_URL=https://example.org/releases/v2 sh install.sh --preset relay --advertise 203.0.113.10
systemctl status echofog-node      # unit создан; с --start служба включена и запущена
```

Первое значение из `--fingerprint` — это SHA-256 целого файла, то самое, что публикуется на сайте и
в README; вторая строка — отпечаток блока ключей, и вместе с правилом `min_version` он описан в
[«Доверие к релизам»](release-trust.ru.md). Сам `--fingerprint` — перекрёстная проверка, а не
доказательство: изменённый скрипт напечатает что угодно, поэтому сверяется значение с сайта и README.
Запускать установщик нужно от root: он создаёт системного пользователя, папку данных и unit systemd,
а с `--start` ещё и включает и запускает службу. Откат на более старую версию требует
`--allow-rollback` и возможен только до подписанного `min_version`; ниже — никогда. Скрипт проверяет
подписи `release.txt` (подписать должны не меньше двух из трёх ключей релиза) и сверяет размер и
SHA-256 бинаря с этой записью; установка начинается только после этого. Передавать скачанное в
оболочку по конвейеру нельзя. До тех пор рабочий путь — Docker, и поэтому следовать нужно разделу 7.
