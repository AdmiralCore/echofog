# Доверие к релизам: ключ в install.sh, min_version, смена ключей

Страница нужна тому, кто публикует релизы, и операторам, которым важно знать, чему именно доверяет путь
установки. Пошаговый гайд по серверу: [deploy-vps-v2.ru.md](deploy-vps-v2.ru.md).

## 1. Что является корнем доверия

Корень доверия установки сервера это **блок публичных ключей релиза внутри `install.sh`** (между строками
`# BEGIN RELEASE KEYS` и `# END RELEASE KEYS`): три ключа Ed25519 и номер эпохи ключей. Это те же ключи
релиза, которыми приложение проверяет собственное обновление (подписать должны два из трёх).

- Скрипт скачивает `release.txt` (короткая текстовая запись: версия, `min_version`, эпоха ключей, размер и
  SHA-256 каждого файла; эпоха это строка `key_epoch`) и `release.txt.sigs` (подписи в текстовой оболочке).
- Он проверяет их командой `ssh-keygen -Y verify` из базовой системы (OpenSSH 8.0 и новее). Другим
  инструментам для этого доверия нет, и ничего скачанное для проверки не запускается. Если `ssh-keygen`
  нет или он слишком старый, скрипт останавливается до скачивания и запуска чего-либо.
- Только после этого он берёт бинарь, сверяет размер и SHA-256 с подписанной записью, делает файл
  исполняемым и запускает. При любом расхождении файл удаляется и скрипт останавливается.
- Установщик ноды (`echofog-node v2 setup`) ещё раз сверяет бинарь с подписанным манифестом. Это второй
  слой, а не первая проверка.

Люди сверяют SHA-256 **всего `install.sh`**, а не только блока ключей: блок ключей говорит, каким ключам
доверять, но остальной файл это логика, которая ими пользуется (проверки, их порядок, порог версии), и
изменённый скрипт с тем же блоком ключей проходить не должен. Команда не исполняет код из файла:

```
sha256sum install.sh
```

Значение меняется с каждым релизом, потому что `install-stamp` записывает в файл порог версии релиза.
Оно публикуется для каждого релиза в двух независимых местах до объявления. `sh install.sh --fingerprint`
печатает то же значение, а второй строкой отпечаток одного блока ключей; это **не** доказательство, потому
что изменённый скрипт может напечатать что угодно.

У блока ключей есть своё значение: SHA-256 точного текста между двумя строками-метками (вместе с метками).
Оно покрывает ключи и эпоху, не меняется, пока не меняются ключи, и именно его называет запись о смене
ключей (раздел 6). Его печатают `install-stamp`, `install-fingerprint --keys ... --key-epoch N` и строка
`keys` в выводе `sh install.sh --fingerprint`.

## 2. Текст для страницы сайта

Значение публикуется в двух независимых местах: на сайте и в README репозитория. Владелец релиза
подставляет значение, которое напечатала команда `efv2-release install-stamp`. Текст для страницы сайта:

> **Проверка install.sh перед запуском.** Нужно скачать файл (`curl --proto '=https' --tlsv1.2 -fsSL -o
> install.sh <адрес>`) и выполнить `sha256sum install.sh`. Значение должно быть в точности таким:
> `<ОТПЕЧАТОК>`. То же значение опубликовано в README репозитория на GitHub; если в двух местах оно
> различается, скрипт запускать не нужно, а проекту нужно сообщить. Передавать скачанное в оболочку по
> конвейеру нельзя.

## 3. Текст для README репозитория

> **Отпечаток install.sh.** Установка серверной ноды использует `install.sh`, в котором лежат
> публичные ключи релиза. Для релиза `<ВЕРСИЯ>` SHA-256 всего файла равен `<ОТПЕЧАТОК>` (эпоха ключей
> `<ЭПОХА>`). Перед первым запуском его нужно сверить со значением на сайте проекта: `sha256sum install.sh`.
> Что проверяется и как меняются ключи, описано в [docs/release-trust.ru.md](release-trust.ru.md).

## 4. min_version и откат

`min_version` это поле подписанного манифеста релиза (поле 8 сообщения `Release`, добавочное изменение:
узлы, которые его не знают, игнорируют поле, а подписи его покрывают). Это самая старая версия, которую
можно ставить или оставлять. Оно копируется в `release.txt` как `min_version`.

- Скрипт и `echofog-node v2 update` отказываются ставить версию **ниже `min_version`** и версию **ниже
  установленной**.
- Откат выше `min_version` требует явного флага (`--allow-rollback` в обоих случаях) и печатает
  предупреждение. Флаг никогда не опускается ниже `min_version`, а скрипт не опускается ниже порога
  версии, вшитого в него при выпуске.
- Манифест, у которого `min_version` выше его собственной версии или не является обычным `X.Y.Z`, не
  считается манифестом.

`min_version` поднимают, когда в старой версии закрыта дыра, которая не должна вернуться. Это
односторонний инструмент: старый манифест его не снизит, потому что старый манифест не принимается вовсе.

## 5. Выпуск релиза

Все шаги выполняются на офлайн-машине владельца релиза. Ключи создаются один раз командой
`efv2-release keygen` на офлайн-носителе; ни они, ни настоящий отпечаток в репозиторий не попадают. В
тестах используются тестовые ключи.

```
efv2-release assemble --version 2.0.1 --min-version 2.0.0 --released-at <UNIX> --artifact ... --out manifest.bin
efv2-release cosign   --manifest manifest.bin --key K2.key --out K2.cosig
efv2-release sign     --manifest manifest.bin --key K1.key --cosig K2.cosig --not-after <UNIX> --out release.bin
efv2-release install-record --manifest manifest.bin --key K1.key --key K2.key --key-epoch 1 --out-dir out/
efv2-release install-stamp  --template deploy/v2/install.sh --keys PUB1,PUB2,PUB3 --key-epoch 1 --floor 2.0.0 --out out/install.sh
```

В папку релиза кладутся `release.bin` под именем `manifest.bin`, `release.txt`, `release.txt.sigs` и
бинари `echofog-node-linux-amd64` и `echofog-node-linux-arm64`; рядом публикуется `install.sh`.
`install-record` отказывается работать меньше чем с двумя разными ключами; `install-stamp` отказывается
штамповать уже проштампованный скрипт и печатает два значения: `file` (SHA-256 всего скрипта) и `keys` (блок
ключей). Готовый скрипт нужно один раз проверить командой `sha256sum out/install.sh` и поместить значение
`file` на сайт и в README **до** объявления релиза. Скрипт, проштампованный заново для другого релиза,
даст другое значение.

### Те же ключи в бинаре

В `install.sh` ключи лежат текстом, в бинаре те же публичные ключи вшиты при сборке. Наборы должны
совпадать, иначе скрипт примет релиз, который нода затем отвергнет (или наоборот). Сборка получает
список в переменной `RELEASE_KEYS`, через запятую:

```
make build VERSION=0.3.0 RELEASE_KEYS='<КЛЮЧ1>,<КЛЮЧ2>,<КЛЮЧ3>'
```

В CI то же значение приходит из секрета репозитория `RELEASE_KEYS`; без него сборка получается
OSS-сборкой. Каждый элемент это публичный ключ Ed25519 в base64 или hex; текстовая форма
`ed25519:<base64url>` инструмента `efv2-release` тоже принимается. Ключи публичные. Приватные ключи
офлайн-машину не покидают.

OSS-сборка вшивает пустой набор: `echofog-node v2 setup` и `v2 update` отвечают «this build has no
release keys», а подписанному списку узлов входа она не доверяет. Это и есть нужное поведение
fail-closed. Непустая, но битая строка не превращается молча в пустую: бинарь падает при старте с
номером плохого ключа, так что сломанная релизная сборка не уйдёт незамеченной.

Для 0.3.0 встроенный список узлов входа подписан одним ключом релиза; манифест обновления уже требует
двух подписей разных ключей релиза. Переход списка на подпись 2-из-3 запланирован после 0.3.0.

## 6. Смена ключей релиза

Старые ключи ручаются за новые, чтобы никому не приходилось доверять новому ключу вслепую:

1. Новый набор ключей создаётся офлайн (три раза `efv2-release keygen`).
2. Публикуется релиз, в манифесте которого новые ключи указаны как `--next-key` (собственный переход
   набора ключей приложения, objects §9).
3. Пишется запись о смене. Она подписывается двумя **старыми** ключами и называет отпечаток нового блока
   ключей и новую эпоху:

   ```
   efv2-release install-rotation --new-keys NEW1,NEW2,NEW3 --new-epoch 2 --key OLD1.key --key OLD2.key --out-dir out/
   ```

   Файлы `rotation.txt` и `rotation.txt.sigs` публикуются в папке релиза и остаются там, пока в ходу
   старые копии `install.sh`.
4. Новый скрипт штампуется новыми ключами и новой эпохой (`install-stamp ... --key-epoch 2`), его значение `file`
   публикуется на сайте и в README, затем выпускается первый релиз, подписанный новыми ключами
   (`install-record ... --key-epoch 2`).

Что делают скрипты: **старый** скрипт (эпоха 1), найдя действительную запись о смене, останавливается,
печатает отпечаток нового блока ключей и просит новый `install.sh`; запись о смене, подписанная кем-то
другим, игнорируется. **Новый** скрипт (эпоха 2) отказывается ставить любой релиз эпохи 1, то есть
завершается раньше, чем появится первый релиз под новыми ключами. Сам скрипт ключи не меняет никогда.

Если ключ релиза украден, запись о смене, подписанная старыми ключами, доверия не заслуживает: новый
отпечаток нужно объявить на сайте и в README по каналам, которые не скомпрометированы, а операторам
сообщить, что `install.sh` нужно заменить вручную.

## 7. Что это не покрывает

- Того, кто контролирует и место, откуда скачивается `install.sh`, и места, где опубликовано значение
  (защита это два независимых места).
- Скомпрометированной сборочной машины или ключа релиза до того, как владелец это заметит; смена ключей
  ограничивает ущерб.
- Системы с подменёнными `ssh-keygen` или `sha256sum`: они часть базовой системы, и им доверяют как ей.
- Тесты в `deploy/v2` запускают настоящий скрипт с тестовыми ключами в чистой системе Debian или Ubuntu;
  запуск на настоящем сервере с настоящими ключами владелец делает при первом релизе.
